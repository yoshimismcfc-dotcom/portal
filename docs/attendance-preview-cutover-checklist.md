# 出欠共有テストから本番運用への切替手順（準備版）

> このファイルは移行の手順書です。追加しただけでは本番切替・個人情報の公開・Firebaseルール変更は行われません。

## 現在の運用
- 試験画面: `attendance-preview.html`。既存の団員・コーチ名簿は Firebase Realtime Database の `members_v2` と `staff/coach` から読む。
- 共有出欠: `attendancePreviewSessions/{sessionId}/answers`（Cloud Firestore）。同じ48桁の `#test=...` を持つリンクを複数端末で使用する必要がある。
- 出欠対象、非表示設定等は、同セッション配下の `eventVisibility`、`holidayExclusions`、`recruitment` に分かれる。
- 端末内の旧試作予定: `yoshimi_smc_attendance_preview_v1`（localStorage）。端末固有の記録は、別端末から自動的には復元できない。
- 既存の本番入口 `attendance.html`、別方式の `attendance-cloud.html` はそのまま維持する。

## 共有テストの確認項目
- [ ] 元から使用している**同一の**共有テストURL（`#test=` 以下を含む）を使う。秘密のトークンを公開Issueやスクリーンショットに書かない。
- [ ] 団員名簿・コーチ名簿の人数と表示名が一致する。
- [ ] 名前をタップして「参加」「未定」「不参加」を更新できる。
- [ ] 既存回答のある複数名で、参加日と連絡事項が以前と一致する。
- [ ] スマホAで更新した内容がスマホBに反映される。ページ再読込後も残る。
- [ ] 休み、祝日、練習、試合、行事の表示がカレンダーと一致する。
- [ ] 予定を出欠対象外にしても消滅せず、再表示・復元できる。
- [ ] CSVの出欠明細・コメント・コーチ分を確認する。
- [ ] 他のコーチ複数人が各自の端末で確認し、修正希望を整理する。

## 本番切替前のデータ保全
1. **まずFirebase Consoleから既存データをバックアップ**する。Realtime Databaseの `members_v2` と `staff/coach` を含め、Firestoreの試験セッションの `answers`・`eventVisibility`・`holidayExclusions`・`recruitment` の現状と件数を記録する。
2. 旧試作画面で使っていた端末固有の予定がある場合、CSV等で別途確保する。ブラウザのサイトデータや履歴は消さない。
3. 元の共有URLとセッションIDを確認し、本番側でも**既存の同一セッション**を参照する方式を原則とする。新しいセッションIDを発行して空の回答表を表示しない。
4. Firestore/Realtime Databaseの保存ルールを無断変更しない。公開範囲と個人情報リスクを承認前に確認する。
5. 既存本番 `attendance.html` の機能（調整さんURL・LINE案内・カレンダー連携等）を調べ、移行時に導線を置き換えてよいか検証する。

## 承認後の切替（未実施）
1. 本番入口の変更専用PRを作成し、既存の試験画面・データ・他ページを残したまま、出欠への導線だけを切り替える。
2. URLのハッシュ（共有セッション識別子）を不用意に落とす遷移を禁止する。URL内の識別子を公開リンクや解析ログへ送信しない。
3. GitHub Actionsのテスト、スマホ実機、複数端末、既存回答の照合を終えてからマージする。
4. リンクの切替後も旧ページを一定期間残し、問題が起きたら**コードと入口だけ**を戻せるようにする。Firestoreの回答データを上書き・消去してロールバックしない。

## 重要な留意点
- 画面のコードを復元してもFirestoreに保存済みの回答を自動的に復旧した証明にはならない。既存のセッションと実データを照合すること。
- URLを知る全員が編集できる運用は、第三者による改変・閲覧の危険がある。氏名や個別の連絡事項の取扱いを確認する。
- 将来の「全員編集」は**追加の管理者ロールを作らない**方針。すでに存在する別方式の認証や権限設定は、承認なしに無効化しない。
