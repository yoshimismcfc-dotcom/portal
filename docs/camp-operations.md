# 合宿管理 導入・運用手順

## 今回の構成

既存のGitHub Pages、HTML/JavaScript、共通デザイン、Firebaseプロジェクトは維持します。ホームとコーチ画面から `camps.html` を開き、独立したHTTPS APIへアクセスします。サーバーは Node.js 24 LTS 推奨（22.16以上）、SQLite、Firebase Admin SDKを使用します。サーバーライブラリは専用 `camp-server/package.json` に分離しています。

現行ポータルは認証なしの公開モードです。このため既存のRTDB保存ヘルパーを合宿の機密情報保存には使いません。既存Firebaseの本番ルールはリポジトリ外のため確認・変更していません。既存名簿 `members_v2` は合宿責任者の取込時にサーバーから読取り、氏名・学年・IDだけ返します。既存会計 `accounting` / `accounting_annual` への自動転記は行いません。

本番サーバーの配置先は未定です。新しい有料契約、外部通知サービス、地図API、公開デプロイは実施していません。GitHub Pages単独ではAPIを実行できません。常時稼働するNodeサーバー、永続ディスク、HTTPS、バックアップ先が必要です。料金は配置先・現在のFirebaseプラン・使用量が未確定のため未算出です。契約前に見積もりと承認が必要です。Google Mapsは利用者が開く外部リンクのみで、APIキーや有料地図SDKは導入していません。

## 導入前に用意するもの

1. Firebase Consoleの管理権限。既存プロジェクトのAuthenticationでEmail/Passwordを有効化し、使用ドメインを承認します。
2. 管理者・責任者・会計担当・コーチ・保護者の利用者アカウント。メール確認を完了してください。APIは未確認メール、匿名ログイン、無効・失効トークンを拒否します。アカウント発行画面は今回の対象外です。管理者がメール確認リンクを発行・案内します。パスワードをコードへ書かないでください。
3. サーバーのFirebase認証資格情報（Application Default Credentials）。トークン失効検査と、名簿 `members_v2` の読取りに必要なIAM権限だけを与えます。サービスアカウント鍵は公開リポジトリ・GitHub Pages・ZIP・ブラウザへ置かず、サーバーのシークレット機構または限定ファイルで管理してください。
4. HTTPSのAPIホスト、永続ディスクと保護されたバックアップ領域。複数インスタンスへSQLiteファイルをコピーして運用しないでください。初期実装は単一プロセス／単一DBです。

## サーバー設定

`camp-server` で以下を実行します。

```sh
npm ci --omit=optional
npm test
```

Firestore・Cloud Storageは使用しないため、任意依存のインストールは不要です。`package-lock.json` の固定版を利用します。

環境変数をプロセスマネージャーまたは安全な環境設定で渡します。

|環境変数|設定内容|
|---|---|
|CAMP_ALLOWED_ORIGIN|既存ポータルのHTTPSオリジン。例：`https://yoshimismcfc-dotcom.github.io`。`/portal`を付けない|
|CAMP_ADMIN_UIDS|システム管理者のFirebase UID。複数はカンマ区切り|
|CAMP_DB_FILE|公開フォルダ・Gitリポジトリ外のDB絶対パス。例：`/var/lib/smc-camp/camps.sqlite`|
|FIREBASE_PROJECT_ID|既存FirebaseプロジェクトID|
|FIREBASE_DATABASE_URL|既存Realtime DatabaseのURL|
|GOOGLE_APPLICATION_CREDENTIALS|ADCをファイルで使う場合の秘密ファイルパス。実行環境でADCが提供される場合は不要|
|PORT|内部ポート。既定8787|

`npm start` で起動します。APIは127.0.0.1にのみ待ち受けます。外部からはHTTPSリバースプロキシを通します。HTTPからHTTPSへの転送、HSTS、要求サイズ64KB以下、適切なレート制限、API応答のキャッシュ禁止を設定してください。Authorizationやリクエスト本文をアクセスログへ保存しないでください。停止・再起動の監視とディスク容量監視も設定します。

ブラウザ側 `camp/config.js` の `apiBase` を実際のHTTPS APIオリジンに変更します。空欄の間は登録を開始できません。APIの公開パスは `/api/camps` と `/api/command` です。管理者が設定を済ませてから既存ポータルの静的ファイルを反映します。DB、秘密情報、node_modulesは公開しません。

## 初回の登録

1. 管理者でログインし、合宿を作成します。春合宿2027候補ボタンは案内に未確定を明記した入力画面を開きます。保存前に確認します。同名・同開始日の重複登録は拒否されます。実データの初期登録は未実施です。
2. 「設定・履歴」から、各利用者のUIDに合宿単位の権限を付与します。利用者自身のUIDはログイン後に表示されます。
3. 参加者を名簿から選びます。参加履歴は氏名・学年のスナップショットとして保持され、元の選手名簿を変えても自動変更されません。
4. 保護者には `parent` 権限を付け、各参加者の `familyUid` にその保護者UIDを設定します。両方が必要です。現在は参加者1人につき保護者UIDを1件保持します。複数保護者アカウントへの対応は未実装です。
5. 運転者を含む全乗車者を参加者に登録します。定員は車内の全員を数えます。位置報告の担当は権限を持つ成人UIDとし、子どもの端末を指定しません。

## 保存・権限・会計の仕様

合宿の集約データはSQLiteの `camps` にJSONとして保存し、合宿全体のrevisionとDBトランザクションで関連更新を一括確定します。30〜40人規模を想定した初期構成です。`participants`、`schedule`、`vehicles`、`rides`、`checks`、`rooms`、`roomAssignments`、`charges`、`payments`、`transactions`、`announcements`、`checklists`、`emergency`、`permissions` を合宿ID内で分離します。資料ファイル用テーブルは未実装です。

`audit` は変更前後、実行者、時刻を記録します。通常の履歴画面には操作のメタ情報だけを返します。健康情報と緊急連絡先は参加者の監査スナップショットに残しません。`requests` は操作IDによる再試行の重複防止に使います。競合時はHTTP 409を返し、古い状態で上書きしません。オフライン編集の永続キューはありません。

保護者には自分の家庭の参加・請求・入金明細に加え、合宿内の家庭別の氏名と未納額を共有します。同じ保護者UIDで集計し、UID未設定の場合は参加者単位です。共有額は参加者別未納額の合計で、過入金と相殺しません。非公開お知らせ、他家庭の請求・入金明細・備考、運営用点呼、会計台帳は返しません。個人の緊急連絡先・健康情報の入力欄は設けず、APIも関連フィールドの登録を拒否します。既存DBに残る関連フィールドもAPIに返しません。施設連絡先・対応手順には個人情報を入力しないでください。保護者が変更できる参加者のフィールドは出欠・宿泊だけです。会計担当は会計に必要な氏名等だけ取得します。権限はブラウザ表示だけでなく、APIの全読書きで検査します。DBファイル自体は公開せず、OS権限でも保護します。

金額は円の整数です。請求は割引を反映した正味額、追加料金は追加請求または額の修正で扱います。入金と返金の差額を参加費収入へ自動集計します。参加費科目の会計手入力は禁止します。未納は参加者ごとに0以上で計算し、他人の過入金で相殺しません。家族まとめ払いは参加者別に配分して登録する運用で、家族一括入力と分配の自動検算は未実装です。入金の取消で返金超過になる場合は先に返金側を訂正します。

## 位置情報・機密情報

位置情報はSQLiteのメモリDBに最新1件のみ保持し、ディスクDBとバックアップには含めません。本人の明示同意と担当成人UID、設定された移動時間（最大12時間）を検査します。位置共有停止はセッションを失効させるため、遅れて届いた更新も拒否します。最新位置は取得から30分または移動終了の早い方で閲覧不可とし、稼働中は毎分削除します。再起動時には消えます。点呼は人が記録した結果だけを使います。

WebのバックグラウンドGPSは保証されません。運転者に操作させず、停車中・同乗する成人が操作します。外部地図共有リンクは外部側の公開設定・失効を別途管理してください。アプリの停止では外部リンクの共有は終了しません。

終了後は責任者が「健康・緊急情報を消去」を実行できます。合宿の配慮事項・緊急連絡先・緊急情報・位置共有を削除します。氏名、会計記録、その他の操作履歴は残ります。DBの論理削除と、バックアップを含む物理的な消去は別です。団の保管方針を決め、過去バックアップの期限削除も実施してください。全参加者の匿名化・保存期限の自動実行は未実装です。

## バックアップ・復旧

`node camp-server/backup.mjs <元DB絶対パス> <新しい保存先絶対パス>` でSQLiteの一貫したバックアップを作成し、`integrity_check` を実行します。既存ファイルは上書きしません。サーバー用アカウントだけが読める保存先に置き、暗号化された保管先と保持期限を設定します。位置情報はバックアップに入りません。

復旧時はAPIを停止し、現在のDBと関連する `-wal` / `-shm` を同じ保護フォルダに退避します。検証済みバックアップを新しいDBパスへコピーし、`CAMP_DB_FILE` を切り替えて起動します。古いWALと混在させないでください。合宿件数・参加人数・集金収支を確認してから利用再開します。初回導入前に実際の配置環境で復旧演習を実施してください。

## 検証コマンド

ルートで `npm test` と `npm run test:camp`。Node 22.16以上が必要です。ブラウザ検査はPlaywrightとChromeを用意し、`node scripts/camp-browser.test.mjs` を実行します。Playwrightを別ディレクトリへ入れた場合は `PLAYWRIGHT_MODULE` にそのパッケージ絶対パスを指定します。`CAMP_QA_OUTPUT` は画像・検証PDF・JSONの保存先です。テスト専用HTTPサーバーと架空認証をスクリプト内で生成し、本番Firebaseには接続しません。本番サーバーに認証バイパス設定はありません。

本番導入前には実際のFirebaseログイン、管理者・保護者の2端末、メール確認・パスワード再設定、HTTPS/CORS、名簿取込、iPhone Safari・Android Chrome、GPS許可/拒否とバックグラウンド制約、プリンター、バックアップ復旧を実施してください。これらは本番環境未設定のため未確認です。

## 残る機能

ネイティブExcel（.xlsx）、領収書画像・資料添付・写真共有、全車両を重ねる地図、LINE・メール・プッシュ通知、家族まとめ払いの一括登録、オフライン再起動と編集自動同期、複数保護者UID、詳細な振り返り分析は未実装です。PDFはブラウザの印刷/PDF保存で、CSVはExcelで開けるUTF-8 BOM形式です。機能のないボタンや架空の保存完了表示は設けていません。
